# 08 — Import, supplier pipelines and synchronization

## 8.1 How it works today

The pipelines are already written in Python and run on the DEV server with a dedicated
PostgreSQL; they publish to WordPress through the PHP routes in `api.php`.

**Vendor A** (dedicated pipeline folder, extensive manual, 35 pytest files):

| Step | Script / class | What it does |
|---|---|---|
| 1–3 | `1_link_category.py` (`Scraper`), `2_link_subcategory.py`, `3_link_product.py` | Crawling categories → subcategories → product URLs |
| 4 | `4_get_product.py` or `4_get_product_api.py` (`StoreApiClient`, `product_data_from_store_api`) | Product page from HTML or from the supplier's **WooCommerce Store API**; append-only history `single_product_change`; 404s in `supplier_source_missing` |
| 5 | `5_product_extract.py` (`EXTRACTproduct`), `extract_utils.py` | Deterministic extraction (regex + JSON mapping): type, model, materials, dimensions, capacity, weight, color, `get_unique_sku` |
| 6 | `6_product_for_sync.py` (`ProductRelations`), `gemini_client.py` | Staging record with EN/IT texts generated by **Gemini** (650–850 character policy, "answer-first"), attributes, categories and tags, prices |
| 7 | `7_scrape_reviews.py` | Supplier reviews |
| 9 | `9_upload_images.py` | rsync + `upload_images_from_folder` route + cover/gallery assignment (manual cover protected) |
| z3 | `z3_send_product_to_wp.py` (`WPProductUploader`) | Creates EN, then IT as a WPML translation; WP IDs in `wordpress_product_sync` |
| 10 | `10_stage_to_live_sync.py` | STAGE → LIVE promotion (flags, media, cross-DB clone, WCFM fixes) |
| 11–13, z4 | `StockSyncer`, `PriceSyncer`, image refresh, product retirement | Recurring post-publication jobs |

Reusable support modules: `supplier_source_state.py` (identity = supplier URL, observations per
variant), `product_change_utility.py`, `stock_state.py` (fail-closed), `supplier_variations.py`,
`image_utility.py` (WebP, EXIF, minimum side 1280), `content_archive.py` (versions of AI texts with
hash), `daily_report.py` + `report_mailer.py`, `execution_safety.py` (write gate, dry-run by
default), JSON mappings (`product_type_map`, `colors_map`, `materials_map`, categories and 164 tags).

**Other vendors**: Vendor B (master XLSX price list for prices and availability; SKUs not in the price list →
out of stock), Vendor D (import and sync scripts with speed-check), Vendor E via the "light" pipeline (`codice_vendor_light/`)
(`source.yaml` per SKU → `enrich_product.py` with Gemini → PDF review sheets → payload in dry-run).

**Encoded business rules** (to be kept):

- The supplier is authoritative for stock: exact quantity; 404 → stock 0, page stays published (SEO).
- Stale data: flagged, never applied.
- Price changes above 15% and products on sale → review; net price = supplier gross / 1.22.
- Supplier identity changes (SKU or model changed, `-copy` pages) → only flagged in the report.

## 8.2 How it will work

The pipelines join the project as the `ingest` app: same codebase, same DB, **no HTTP hop
to PHP**, no STAGE → LIVE promotion. Jobs run in the worker (dedicated container,
which can be moved to another machine if scraping requires it). The `/api/v1` API remains for vendors who
sync on their own (advanced plan) and for any external pipelines.

### Structure

```
apps/ingest/
  adapters/
    base.py            # SupplierAdapter (Protocol)
    html_scraper.py    # current steps 1–4 (Vendor A)
    woo_store_api.py   # generic: any WooCommerce supplier (from 4_get_product_api.py)
    xlsx_pricelist.py  # Vendor B

  enrich/              # GeminiClient behind TextEnricher, prompts and policies, content_archive
  images.py            # image_utility.py
  state.py             # supplier_source_state, product_change_utility, stock_state, missing/image state
  publish.py           # from staging to catalog via catalog.services.upsert_products
  jobs.py              # scheduled tasks
  reports.py           # daily_report, report_mailer
```

### Staging models

```python
class SupplierSource(Model):       vendor; adapter_code; config (JSON); schedule; is_active
class SourceItem(Model):           source; source_url (identity); aliases; product (FK, null); last_seen_at; missing_since
class SourceObservation(Model):    item; observed_at; payload (JSON); payload_hash   # append-only, no duplicate versions
class ProductDraft(Model):         item; extracted (JSON); enriched (JSON per language); status (new|ready|needs_review|published|rejected)
class ImportRun(Model):            source; kind (scrape|stock|price|images|publish); started/finished; dry_run; counters; log
class ReviewItem(Model):           run; product; kind (price_jump|sale|identity_change|stale|duplicate_sku); payload; resolved_by
class MappingTable(Model):         vendor; kind (category|term|color|material…); key; target (generic FK); aliases
```

The current JSON maps become `MappingTable` entries with **FKs** to categories and navigation taxonomy terms (no longer
per-language WordPress IDs), editable from admin and versioned.

### Contracts

```python
class SupplierAdapter(Protocol):
    code: str
    def discover(self, source: SupplierSource) -> Iterable[SourceRef]
    def fetch(self, ref: SourceRef) -> RawObservation          # HTML, JSON, XLSX row, YAML
    def extract(self, raw: RawObservation) -> ExtractedProduct # Pydantic, validated

class TextEnricher(Protocol):                                   # interchangeable AI provider
    def describe(self, product: ExtractedProduct, lang: str, policy: TextPolicy) -> EnrichedText
    def translate(self, text: EnrichedText, target: str) -> EnrichedText

def plan_stock_actions(observations, products) -> list[StockAction]   # pure function (from StockSyncer)
def plan_price_actions(observations, products, max_change_pct=15) -> list[PriceAction]  # from compute_price_actions
def publish_drafts(drafts, *, dry_run=True) -> ChangeSet                 # calls catalog.services
```

Rules: dry-run by default; switching to write mode requires a per-source flag (replacing the
marker files of `execution_safety.py`); AI output is validated against schema and policy before
becoming a draft; generated translations have status `machine` and require review if the vendor's
policy says so; `(vendor, sku)` uniqueness is enforced by the DB (the 29 current duplicate SKUs are
resolved during migration, see [13](13-migration-cutover.md)).

### Onboarding a new vendor (standard procedure)

1. Choose the adapter (WooCommerce Store API, scraping, XLSX/CSV, YAML light).
2. Configure the `SupplierSource` and the `MappingTable` entries (categories, navigation taxonomy terms, colors, materials).
3. First run in dry-run → report with drafts, missing mappings, missing GPSR fields.
4. Review of the drafts (AI texts, images) → scheduled publication.
5. Activation of the recurring stock and price jobs.

Goal: a vendor with a WooCommerce website is activated **without writing code**.
