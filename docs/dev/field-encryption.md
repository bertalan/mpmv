# Field-level encryption

Some columns are encrypted at rest, so a database dump, a backup or a read-only SQL session does
not expose them (spec 12, backlog SEC.3). The key lives outside the database and can be rotated.

## What is encrypted

| Model | Field | Why |
|---|---|---|
| `vendors.Vendor` | `iban` | Bank details (VEN.12) |
| `vendors.Vendor` | `tax_code` | DAC7 TIN; for a sole proprietor, a personal identifier (codice fiscale) |

Deliberately in clear: the VAT number (public in VIES, searched by staff, checked against
VIES), names and addresses (printed on order confirmations and commission statements, and searched). A company's tax code is often
its VAT number, which stays readable in `vat_number`; the case encryption protects is the
personal one.

Encrypted fields are also **masked in the audit log** (`apps.vendors.services.MASKED_FIELDS`):
an encrypted column is pointless if the audit row copies the value in clear. A unit test fails
when a vendor field is encrypted but not masked.

Planned users of the same fields: KYC data and payout accounts (VEN.6), DAC7 date of birth
(CMP.1). KYC *documents* are files: they need encrypted storage, not a model field. TOTP secrets
(django-otp) are not encrypted yet: that is an open question for the owner.

## How it works

- `apps.core.crypto` (pure): AES-256-GCM from `cryptography`, a random 96-bit nonce per value.
  A stored value is a token `enc1:<key id>:<base64url(nonce | ciphertext | tag)>`. The column
  name (`app_label.model.field`) is the associated data, so a token copied into another column
  does not decrypt.
- `apps.core.fields.EncryptedCharField` / `EncryptedTextField`: Python code sees the
  plaintext; the column is `text`. `max_length` still validates the plaintext. Empty strings and
  NULL are stored as they are.
- A value that does not decrypt (wrong or missing key, cleartext, tampering) raises
  `apps.core.crypto.DecryptionError`. There is no silent fallback.
- Only `field=""` and `field__isnull` work in queries. Anything else (`=value`, `icontains`,
  `in`, transforms) raises `FieldError`, because the ciphertext is randomized and a search would
  silently match nothing. Ordering by an encrypted field (`order_by`, `Meta.ordering`, an
  admin column) raises `FieldError` too: the order of random ciphertexts means nothing.

### Searching (blind index)

No encrypted field needs a lookup today, so there is no blind index. If one ever does (e.g.
"is this TIN already registered?"), add a separate column with a keyed HMAC-SHA256 of the
normalized value, under its own key, and query that. Do not decrypt whole tables in Python.

## Keys

A key is `<key id>:<base64url of 32 random bytes>`. The settings read
`MPMV_FIELD_ENCRYPTION_KEYS` (comma-separated) or the file named by
`MPMV_FIELD_ENCRYPTION_KEYS_FILE` (one key per line, `#` comments). Keys are listed **newest
first**: the first one encrypts, all of them decrypt.

```sh
uv run python manage.py generate_field_key 2026-11     # prints "2026-11:<key>"
```

| Environment | Where the key comes from |
|---|---|
| Tests | Generated by `mpmv/settings/test.py` for each process; never written anywhere |
| Local dev | Generated once into `~/.config/mpmv/dev-field-keys` (mode 600), outside the repo |
| Local stack (`make dev`) | Generated once into the git-ignored `build/dev-stack.env` |
| CI image job | Generated for the run |
| STAGE / LIVE | `~/.config/mpmv/mpmv.env` on the host (`deploy/server/mpmv.env.example`), or a key file |

Back the keys up **separately** from the database backups (pgBackRest, OPS.1): a backup and
its key in the same place protect nothing, and a lost key means lost data.

### Checks

- `core.E301` / `core.E302` (every `manage.py` command): no key, or a malformed one. The
  message never shows key material.
- When a database is checked (`migrate` always does it; also `manage.py check --database
  default`), one sample per key id and column is decrypted:
  - `core.E303`: values use a key id that is not configured (a key retired too early);
  - `core.E304`: a configured key does not decrypt (wrong key under the right id);
  - `core.W301`: values still use an older key (rotation pending);
  - `core.W302`: values are stored in clear (e.g. restored from an old dump).

A deploy with a wrong key therefore stops at the `migrate` step.

## Rotating a key

1. `manage generate_field_key <new id>` and put the new key **first**, keeping the old one
   after it. Deploy: new values use the new key, old values still decrypt.
2. `manage rotate_field_keys --dry-run` lists the objects to rewrite (key ids only, never
   values); `manage rotate_field_keys` rewrites them in one transaction, with rows locked, and
   writes one `core.field_keys.rotated` audit entry per object. It also encrypts values found
   in clear. A wrong key makes it fail before anything is written.
3. `manage check --database default` shows no `core.W301`. Remove the old key and deploy.

## Adding an encrypted field

1. Use `EncryptedCharField` (or `EncryptedTextField`) on the model.
2. Mask it in the model's audit snapshot.
3. For an existing column, write a migration: `AlterField`, then
   `RunPython(encrypt, decrypt)` with `apps.core.encryption.encrypt_column` /
   `decrypt_column` (see `apps/vendors/migrations/0008_encrypt_iban_and_tax_code.py`), and a
   migration test.
4. Extend the database dump test (`apps/vendors/tests/integration/test_field_encryption.py`).
